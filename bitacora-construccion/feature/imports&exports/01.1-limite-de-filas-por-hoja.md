## Necesidad

El arranque real de E5.1 dejó una hoja con 5.001 filas: ni importar, ni enviar, ni aplicar comprobaban un máximo. El plan lo dejó como pendiente antes de E5.2.

## Ajustes al escribir el código

- **`RevisionPointer` lleva `rowCount`.** Solo dos consultas lo construyen (`findHead` de borradores y de importaciones); las dos leen `row_count` de la revisión. Así los avisos tempranos no necesitan otra consulta.
- **`rowCountChange` reutiliza `resultingRows` y `mentionedRowIds`**: filas vivas después menos filas mencionadas que estaban vivas antes. Sirve igual para un borrador manual (insertar, borrar, editar) que para una importación (`append` solo inserta; `upsert` además edita, que no cuenta).
- **En `submit` el recuento se hace sobre la revisión actual** (`head.rowCount` + cambio sobre las filas del head). Al enviar, head y base coinciden, así que es el mismo número que tendrá al aplicar.
- **La comprobación al aplicar no se alcanza por HTTP con el flujo normal**: aplicar exige que el head no haya cambiado desde el envío, y el envío ya comprobó. Se mantiene como la regla que manda (por ejemplo, borradores aprobados antes de este cambio) y se prueba en integración, creando el borrador aprobado desde el repositorio.

## Implementación

- `POST P/worksheets/:worksheetId/imports` → **409 `WORKSHEET_ROW_LIMIT_EXCEEDED`** si las filas actuales más las que el archivo inserta pasan de 5.000. No se guarda nada.
- `GET P/changesets/:id/diff` → `review.resultingRowCount` (campo nuevo, se añade sin cambiar los demás).
- `POST P/changesets/:id/submit` → 409 con el mismo código si `resultingRowCount` pasa de 5.000.
- `POST P/changesets/:id/apply` → 409 si el recuento dentro de la transacción pasa de 5.000; el borrador sigue aprobado y no queda nada escrito.

## Consecuencias

- Una hoja no puede pasar de 5.000 filas por ningún camino de escritura. Subir el límite es cambiar una constante, después de medir (T34).
- La web puede usar `resultingRowCount` para avisar antes de enviar.
- **Nota del arranque real:** con `AppModule` completo, el pool de 5 conexiones de las pruebas cruza las consultas de los workers en PGlite («unnamed prepared statement does not exist»). Es una limitación de PGlite, que atiende una sola conexión real; el script de arranque usa un pool de una conexión. Las suites no se ven afectadas porque no montan los workers.
