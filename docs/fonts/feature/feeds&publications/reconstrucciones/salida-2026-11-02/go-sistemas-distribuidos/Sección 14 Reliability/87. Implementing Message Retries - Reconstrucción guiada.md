## Objetivo de la lección

Envolver el procesamiento de cada mensaje de RabbitMQ en un reintento con espera creciente y un máximo de intentos; al agotarlos, anotar en el mensaje por qué falló y rechazarlo sin reencolar, y confirmar (ack) solo cuando el handler termina bien.

## Estado inicial heredado

El consumidor de RabbitMQ llama al handler una vez por mensaje. Si el servicio de pagos está caído, el mensaje queda sin confirmar en la cola indefinidamente, sin alertas. Existe en `shared` un paquete `retry` del código inicial del curso.

## Fase 1 — Envolver el handler en un reintento con espera creciente

**Objetivo:** Envolver el handler en un reintento con espera creciente.

**Código o cambio acumulativo:**

```text
cfg := retry.DefaultConfig()

err := retry.WithBackoff(context.Background(), cfg, func() error {
	return handler(ctx, d)
})
```


**Por qué:** Un fallo transitorio (servicio caído un momento) se resuelve solo; la espera creciente evita martillear al servicio.

**Cómo comprobarlo y resultado esperado:** Con el handler forzado a fallar, el log muestra intentos tras 1, 2 y 4 segundos.

**Procedencia:** E1 / E2 / E4 / E5 / E6 / E7 / E14.

## Fase 2 — Al agotar los intentos: anotar el motivo y rechazar

**Objetivo:** Al agotar los intentos: anotar el motivo y rechazar.

**Código o cambio acumulativo:**

```text
if err != nil {
	log.Printf("Message processing failed after %d retries for message %s: %v", cfg.MaxRetries, d.MessageId, err)

	headers := amqp.Table{}
	if d.Headers != nil {
		headers = d.Headers
	}

	headers["x-retry-count"] = cfg.MaxRetries
	headers["x-death-reason"] = err.Error()
	headers["x-original-exchange"] = d.Exchange
	headers["x-original-routing-key"] = d.RoutingKey
	d.Headers = headers

	_ = d.Reject(false)
	return err
}
```


**Por qué:** Un mensaje que no se puede procesar no debe quedarse para siempre: se marca con lo necesario para investigarlo (intentos, motivo, origen) y sale del flujo normal.

**Cómo comprobarlo y resultado esperado:** En RabbitMQ el mensaje aparece como rechazado y ya no está en la cola.

**Procedencia:** E3 / E8 / E9 / E10 / E12 / E13.

## Fase 3 — Confirmar solo tras el éxito

**Objetivo:** Confirmar solo tras el éxito.

**Código o cambio acumulativo:**

```text
_ = d.Ack(false)
return nil
```


**Por qué:** Si el proceso cae antes de confirmar, el broker puede volver a entregar el mensaje.

**Cómo comprobarlo y resultado esperado:** Un mensaje procesado bien desaparece de la cola con ack.

**Procedencia:** E11.

# Resumen mental

Reintentar con espera creciente y un máximo; al agotar los intentos, el fallo se vuelve definitivo, se guarda el motivo y el trabajo sale del flujo normal. Confirmar el éxito solo al final.
