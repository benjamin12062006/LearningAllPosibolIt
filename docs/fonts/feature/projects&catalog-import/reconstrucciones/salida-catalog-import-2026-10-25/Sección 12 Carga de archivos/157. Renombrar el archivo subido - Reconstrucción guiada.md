## Objetivo de la lección

Asignar un nombre UUID a cada imagen recibida mediante el callback filename de diskStorage y organizar los helpers mediante un archivo de barril.

## Estado inicial heredado

El endpoint Files/product ya usa fileFilter y recibe un archivo obligatorio. La lección 156 añade diskStorage para escribirlo en ./static/uploads; la 157 cambia el destino a ./static/products y personaliza filename. El filtro creado en la 155 se hereda sin cambios. FilesModule y FilesService del recurso siguen como contexto, no se inventan sus archivos.

## Fase 1 — Configurar la asignación del nombre físico

**Objetivo:** Configurar la asignación del nombre físico.

**Código o cambio acumulativo:**

```ts
storage: diskStorage({
  destination: './static/products',
  filename: fileNamer,
})
```


**Por qué:** El almacenamiento de disco invoca filename con su callback. No se usa directamente originalname para seleccionar el nombre físico; aquí solo se configura el lugar del ejemplo.

**Cómo comprobarlo y resultado esperado:** En el curso, observar que filename recibe la carga y destination apunta a products. La ruta local no es una URL pública.

**Procedencia:** E1 / E2 / E6 / E8.

## Fase 2 — Sustituir el nombre fijo por un UUID

**Objetivo:** Sustituir el nombre fijo por un UUID.

**Código o cambio acumulativo:**

```ts
import { v4 as uuid } from 'uuid';

const fileExtension = file.mimetype.split('/')[1];
const fileName = `${uuid()}.${fileExtension}`;
callback(null, fileName);
```


**Por qué:** El nombre fijo reutiliza el mismo destino y puede sobrescribir. El UUID genera una identidad para cada carga; mantener extensión de imagen es una decisión del ejemplo, no una validación del archivo.

**Cómo comprobarlo y resultado esperado:** En el proyecto original, repetir una carga debe producir nombres diferentes. La prueba no demuestra qué ocurre ante una colisión de filesystem ni implementa creación exclusiva; ese detalle no se añade al curso.

**Procedencia:** E2 / E3 / E5.

## src/files/helpers/fileNamer.helper.ts

Procedencia: E1/E2/E5: helper, callback y UUID; la firma y rama defensiva vienen del helper de filtro anterior descrito en 155. La rama false conserva el estilo del curso y no se presenta como el tipo correcto que deba copiar un adaptador nuevo. Mensajes/identificadores se normalizan según certeza inicial.

```ts
import { v4 as uuid } from 'uuid';

export const fileNamer = (
  req: Express.Request,
  file: Express.Multer.File,
  callback: Function,
) => {
  if (!file) return callback(new Error('File is empty'), false);

  const fileExtension = file.mimetype.split('/')[1];
  const fileName = `${uuid()}.${fileExtension}`;
  callback(null, fileName);
};
```

## src/files/files.controller.ts

Procedencia: E6/E8: storage y destino; E4: helpers; E9 y 155: respuesta/guard de archivo heredados; E1/E5: filename. Scaffold y imports se ensamblan desde el recurso del curso. No se inventa una respuesta con URL, checksum o tabla que esta clase no construye.

```ts
import { BadRequestException, Controller, Post, UploadedFile, UseInterceptors } from '@nestjs/common';
import { FileInterceptor } from '@nestjs/platform-express';
import { diskStorage } from 'multer';
import { FilesService } from './files.service';
import { fileFilter, fileNamer } from './helpers';

@Controller('files')
export class FilesController {
  constructor(private readonly filesService: FilesService) {}

  @Post('product')
  @UseInterceptors(FileInterceptor('file', {
    fileFilter,
    storage: diskStorage({
      destination: './static/products',
      filename: fileNamer,
    }),
  }))
  uploadFile(@UploadedFile() file: Express.Multer.File) {
    if (!file) {
      throw new BadRequestException('Make sure that the file is an image');
    }
    return { fileName: file.originalname };
  }
}
```
