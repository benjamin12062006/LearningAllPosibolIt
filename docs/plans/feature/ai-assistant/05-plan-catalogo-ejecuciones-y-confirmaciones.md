## Resultado buscado

Una persona inicia un run a partir de su mensaje guardado y recupera por consulta el resultado en Nest. FastAPI usa un modelo simulado y el catálogo acotado al contexto de la ejecución. Una lectura devuelve datos autorizados. Una escritura preparada presenta un diff o resumen emitido por Nest y solo se materializa cuando la persona confirma. Los cambios de hoja siguen el flujo de borrador y revisión humana.

### Catálogo y proyecciones C7

Los resolvers y controladores de la persona siguen usando sus servicios. La ruta que recibe al modelo admite un nombre registrado y argumentos para ese nombre. La API pública `/api/graphql` sigue aceptando la sesión habitual. Los contratos compuestos de C7 se reutilizan como referencia de campos y límites. Si una lectura necesita ejecución GraphQL, hacerlo dentro de Nest con una operación fija seleccionada por el catálogo, variables construidas por Nest y autorización acotada al run. El cliente FastAPI no recibe capacidad de enviar un documento GraphQL, alias, fragmento, selección o nombre de operación libre. La implementación debe demostrar paridad con los servicios antes de habilitar un documento. Con llamadas directas al servicio se verifica forma y alcance contra la proyección de C7 que corresponda.

| Primer recorrido | Registro y servicio previstos |
| --- | --- |
| Resumen e inventario del proyecto | `get_project_overview`, lecturas de `ProjectsService` y los módulos del contrato `ProjectSummary`, con `projectId` aportado por el run y recuentos paginados. |
| Libros, hoja, columnas y filas | `get_sheet_schema` y `query_rows`, reutilizando `WorksheetsService` y `WorksheetRowsService`. Fijar revisión explícita y acotar filas a 100 por llamada. Para transformar una selección utilizar H6. |
| Catálogo, reglas y evaluaciones | Estado/resumen de importación y catálogo, reglas y revisión vigente, `get_evaluation_report` y vista previa determinista. Usar proyecciones de C7 para evaluación y reglas. Usar el servicio de importaciones para informes y mapeos; extraer campos de negocio, sin claves de artefactos, opciones de origen ni recibos. |
| Feed y visor | `get_feed_status` y `list_feed_products` sobre `FeedsService` y `FeedViewerService`; proyección de diagnóstico y recuentos sin enlaces que lleven tokens. |
| Borradores y vistas | `get_proposal_diff`, `preview_transform({ selectionId, columnIds, transform })` y preparación de `create_change_proposal({ previewId, explanation })` y `propose_sheet_layout({ name, purpose, columns })`. Integrar las tres herramientas H6 con sus referencias de selección y preview a través del run. `suggest_view` propone definición de vista al humano y usa el servicio de vistas solo tras confirmar. Las plantillas de mapeo usan su servicio y las escrituras quedan sujetas a preparación y confirmación. |
| Búsqueda y aclaración | Reservar los nombres fijos de FastAPI. `search_knowledge` pasa por el guard de Nest y llama desde Nest a la búsqueda autenticada de FastAPI con el proyecto del run. `ask_for_clarification` permanece local y devuelve su desenlace al run. |

Para cada herramienta, registrar la operación pública o caso de uso de referencia, clase de efecto y campos devueltos. Evaluar las operaciones restantes que C7 tenía como candidatas de acuerdo con su efecto y su preparación disponible. `CreateRuleset` y `RequestEvaluation` sirven como contrato de forma para una futura confirmación del mismo servicio; activar cada escritura solo cuando pueda probarse su resultado recuperable y su revalidación dentro de una transacción, o el encolado idempotente en esa transacción. Operaciones como `ProposeChange` que envían a revisión, o las que crean una hoja oficial directamente, no sustituyen las variantes de H6. Conservar la lista comprobable de 24 exclusiones de C7 y comprobar también administración de miembros, chat privado, entrega, archivos multipart, credenciales y demás operaciones humanas ajenas al catálogo. La prueba debe cerrar por defecto ante cualquier nombre desconocido.

## Persistencia y transacciones

| Tabla | Campos y restricciones previstos |
| --- | --- |
| `ai_runs` | ID UUID, organización/proyecto, conversación, mensaje disparador, actor, selectores de inicio normalizados, contexto resuelto y versión de contrato, estado, timestamps de cola y ejecución, plazo del run/reclamo, hash de credencial temporal, ID de reclamo y resultado o error público. Guardar el identificador del mensaje asistente con unicidad. Usar FK al mensaje en la misma conversación, y ámbito/actor derivados de esta. `queued`, `running`, `succeeded`, `failed`, `expired` corresponden a persistencia. `cancelled` se activa en E6.4. |
| `ai_tool_calls` | Clave `(run_id, call_id)`, operación, modo, hash de argumentos canónicos, estado, `target` de alcance acotado y datos necesarios para recuperar la respuesta limitada. Registrar la llamada dentro de la transacción que comprueba el reclamo, y limitar a ocho llamadas aceptadas por run además del límite de FastAPI. Una llamada en curso repetida no vuelve a ejecutar. Si cambia operación, modo o entrada, 409. Guardar solo el contenido indispensable para deduplicar y resolver el resultado. |
| `ai_run_proposals` | UUID, FK al run y la llamada que la prepara, una por run, nombre y versión de operación, referencia canónica al efecto de H6 o plan tipado, ámbito, base/revisión, hash, vencimiento, resumen, estado y resultado humano. Transiciones `prepared → ready → confirmed/rejected`; una preparación de un run fallido queda inutilizable. Un run expirado no publica sus preparaciones. Si el estado final pide confirmación, validar coincidencia del `proposalId` y persistir `ready` junto al mensaje asistente. |

Las escrituras toman bloqueos en el orden organización → run → preparación → recurso de dominio, y vuelven a comprobar permisos, plazo, estado y revisión. Para reclamar de la cola se debe evitar invertir el orden de bloqueo en la misma transacción. La llamada a FastAPI y otras operaciones de red quedan fuera de los bloqueos. Para las lecturas que cruzan el servicio se revalida el acceso antes de devolver resultados si una revocación o cancelación se confirmó entretanto. Mantener `target` derivado de ámbito, argumentos validados, selección materializada y resultado autorizado. Ejemplos de campos son IDs de hoja, filas, columnas, evaluación o feed. Los eventos de E6.4 podrán reutilizar la misma referencia sin incluir valores de celdas.

### Confirmación humana

1. Resolver la sesión, pertenencia y propiedad de conversación/run. Una propuesta ajena responde 404.
2. Validar permiso de confirmación de la operación, recurso activo, plazo y el hash/revisión de la propuesta que vio la persona. El cliente identifica la propuesta y su hash, y Nest toma el efecto del registro preparado. Si el mismo actor reintenta una decisión ya confirmada con el hash original, recuperar el resultado autorizado aunque ya haya caducado el preview. Comparar primero la decisión y el hash para rechazar carreras con el comando opuesto.
3. Revalidar el plan con el dominio. Para una edición de H6, llamar al helper transaccional que inserta el changeset sobre la misma base y guarda auditoría. Para el diseño de hoja, guardar el borrador `initialize_sheet` de H6, con sus columnas y sin datos de inventario. En ambos casos se crea estado de borrador. El envío, la aprobación y la aplicación siguen sus rutas humanas.
4. Actualizar el estado y el resultado humano en la misma transacción que crea el borrador o registra el trabajo idempotente. Si falla la transacción, queda en `ready` y puede reintentarse mientras la base y el plazo sigan vigentes. Un rechazo deja registrado el resultado y evita confirmar después. El historial siguiente puede aportar el estado de la propuesta y el ID del borrador como referencia resuelta por Nest, dentro de su propio presupuesto de contenido.

## Contratos

`P` es `/api/v1/organizations/:organizationId/projects/:projectId`. Todas estas rutas requieren Descope, resuelven privacidad de conversación antes de exponer su estado y usan los permisos vigentes del recurso.

| REST | Entrada y salida | Proyección GraphQL para Nuxt |
| --- | --- | --- |
| `POST P/conversations/:conversationId/runs` | `{ messageId, context? }` → 202 `{ run }`. Campos de `context` admitidos por el caso de uso: revisión, borrador si existe, y selección de filas/columnas o filtro. | `startAgentRun` |
| `GET P/ai-runs/:runId` | 200 `{ run }` con estado, resultado acotado, referencia al mensaje y propuesta pública si existe, con `proposalHash` y referencias de revisión autorizadas. | `agentRun` |
| `POST P/ai-runs/:runId/proposals/:proposalId/confirm` | `{ proposalHash }` → 200 con resultado persistido. | `confirmAgentProposal` |
| `POST P/ai-runs/:runId/proposals/:proposalId/reject` | `{ proposalHash }` → 200 con estado rechazado persistido. | `rejectAgentProposal` |

Lectura del historial y conversación según E6.2. Sus rutas siguen funcionando aunque el agente no esté configurado. Iniciar un run sin servicio configurado devuelve 503. Los estados de resultado de FastAPI son `answered`, `confirmation_required`, `needs_clarification` y `limit_reached`. Se guardan como desenlaces de `succeeded`. Un fallo de red, validación de la respuesta o expiración queda en el estado y error público correspondientes. Añadir las cuatro rutas humanas a la matriz C7 con sus equivalentes de GraphQL y la pasarela como HTTP interno. Actualizar los recuentos sobre la matriz resultante de E6.2 y H6.

**Nest → FastAPI.** `POST /v1/agent/runs`, Bearer de servicio. Reutilizar el cuerpo actual y añadir `context` al DTO estricto y a `AgentRun` a la vez. `scope.projectIds` contiene solo el proyecto autorizado. Contexto tipado por modo proyecto/libro/hoja, con libro, hoja y revisión autorizados cuando correspondan. Si se ofrece una selección, incluir su ID opaco, recuento y columnas. Autor, cookies, credenciales, payload del navegador y filas enteras quedan fuera del contexto del modelo. `message` se toma del disparador y `history` de las entradas anteriores a su secuencia (hasta 50, en orden y con límite acumulado de bytes), dentro de la misma conversación. La respuesta de FastAPI se valida como unión de desenlaces. Para `confirmation_required` el DTO añade `proposalId` devuelto por Nest y lo conserva hasta la respuesta. El resultado público se arma desde la propuesta persistida.

**FastAPI → Nest.** `POST /internal/v1/agent-runs/:runId/operations/:name` con Bearer del run y cuerpo `{ callId, mode, arguments }`. FastAPI genera un UUID por invocación aceptada y lo propaga por su puerto de operaciones. Al preparar se devuelve `{ proposalId, summary }`; al leer se devuelve JSON acotado. Usar la validación de DTO existente y un validador de argumentos vinculado al esquema publicado en el catálogo. `execute` autoriza solo lecturas y `prepare` solo escrituras candidatas. Añadir la exclusión exacta al prefijo global de Nest y declarar el controlador neutral a la versión para conservar la URL de A11. Responder con los códigos públicos de Nest, sin detalles sobre la credencial. Un cuerpo/args inválidos 400, credencial ausente o incorrecta 401, falta de permiso en ámbito visible 403, recurso ajeno/nombre desconocido 404, uso de callId con otro contenido o preparación incompatible 409. FastAPI mantiene el error genérico para 401 y 5xx. El worker invalida la credencial al cerrar el run.

## Incrementos

1. Crear migración local, servicio de creación, lectura privada y worker con resultado y mensaje asistente atómico. Probar idempotencia del disparador, un solo run activo, expiración del reclamo y arranque con la IA deshabilitada.
2. Introducir el catálogo y la pasarela con autenticación por run. Integrar lecturas de proyecto/hoja/reglas/evaluación/feed y búsqueda acotada. Verificar la matriz de exclusiones, proyecciones y límites de filas, llamadas y respuesta.
3. Añadir preparación de H6 y confirmación/rechazo humanos, con plan canónico, hash, resultado persistido, referencias de auditoría y soporte transaccional de los dominios incorporados. Validar el contexto de ejecución y la coincidencia del `proposalId` en FastAPI.
4. Montar resolvers humanos y ampliar la matriz y los contratos C7. Ejecutar el recorrido entre Nest y FastAPI con LLM guionizado, registrar ajustes y completar la bitácora. Dejar las rutas de consulta y el reclamo utilizables por E6.4 para añadir SSE, cuotas y cancelación.

## Comprobación prevista

| Área | Criterio |
| --- | --- |
| REST y GraphQL | Ausencia de sesión, 404 para conversación/run ajenos de la misma o distinta organización, 403 por Viewer o degradación y 409 por archivado. Verificar dos organizaciones, dos personas, Editor/Manager, coincidencia de contrato C7 y rechazo del token de run en endpoints públicos. |
| Catálogo y credencial | Recorrer las 24 exclusiones, comprobar árbol de DTO/esquema y permiso, modo incompatible, IDs ajenos aun usando una credencial válida, vencimiento, cancelación/terminal y llamada fuera de su run. Probar que una instrucción en datos de hoja permanece contenido y que el ámbito de búsqueda de conocimiento sigue al run. |
| Consistencia | Dos arranques concurrentes para el mismo mensaje dejan un run. Un segundo mensaje concurrente encuentra uno activo. Dos workers tienen un dueño para el reclamo. Una respuesta tardía, el restart, un timeout y el apagado dejan estados recuperables. Las decisiones repetidas o concurrentes dejan un solo borrador y ningún efecto oficial. Probar rollback mediante fallo entre creación del borrador y escritura del resultado. |
| Integración local | Nest real sobre PGlite y FastAPI real sobre HTTP. Usar `ScriptedResponses`, embeddings deterministas y Qdrant en memoria o el adaptador de prueba que conserve la misma frontera HTTP. Leer una hoja, preparar un 5 % sobre su selección, confirmar con sesión, recuperar mismo borrador al reintentar y verificar revisión vigente intacta. Probar también resultado de aclaración, respuesta malformada del proveedor, contexto desfasado y rechazo de layout antes de crear hoja. |
| Defectos a propósito | En una copia temporal, saltar la comprobación del actor/ámbito, aceptar el token vencido, invertir `prepare`/lectura, registrar una operación prohibida, permitir una segunda propuesta/llamada con el mismo ID y confiar en el plan que devuelve el modelo. Probar además doble confirmación, omitir la comprobación de revisión y romper atomicidad entre borrador y resultado. |
| Cierre | TypeScript, lint, formato, suites de Nest y `make check` de FastAPI en serie. Verificar migraciones locales, diff vacío contra Prisma y arranque real. Contrastar bloqueos e índice parcial en PostgreSQL multiconexión de pruebas cuando esté disponible. |

E6.4 incorpora SSE, cancelación y cuotas. E6.6 fija el contrato de chat y su endurecimiento para Nuxt. La cobertura de escritura se amplía por operación solo después de comprobar sus efectos y su confirmación. Las migraciones de datos compartidos siguen el procedimiento del workspace.
